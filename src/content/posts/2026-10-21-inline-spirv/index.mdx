## Why inline SPIR-V?

When you compile HLSL for Vulkan, DXC turns your shader into SPIR-V. SPIR-V can express more than HLSL lets you write. Some instructions have no HLSL function, some options can't be passed, and some types have no HLSL name.

With **inline SPIR-V**, you write a small declaration in HLSL that tells DXC "a call to this function is exactly this SPIR-V instruction". Then you call it like any other HLSL function.

There are three good reasons to learn it.

1. **Use SPIR-V features that HLSL doesn't expose (yet).**
   Explicit barrier and memory control, subgroup operations HLSL doesn't have, and new SPIR-V extensions not exposed in HLSL. Another good example is atomics: HLSL's `Interlocked*` functions don't let you choose [memory ordering](https://en.cppreference.com/cpp/atomic/memory_order); DXC always emits them as *relaxed*.
2. **Atomics on memory you reach through an address.**
   Atomic functions like `InterlockedAdd` work on `groupshared` variables and buffer elements. Inline SPIR-V lets you run atomics with BDA (*buffer device address*) too. (More recently, `vk::BufferPointer` was added to DXC, which allows it, but only with relaxed ordering.)
3. **More modular code.**
   Once an instruction is wrapped in a small HLSL function, you can reuse it everywhere and build your own library on top, like we do in [Nabla](https://github.com/Devsh-Graphics-Programming/Nabla/tree/master/include/nbl/builtin/hlsl/spirv_intrinsics).

## SPIR-V recap

### `OpVariable` is a pointer

<HlslSpirv html={opVariable} />

The first two lines are only type definitions; nothing exists in memory yet. The third line, `OpVariable`, is where real memory comes in. And notice its type: `OpVariable` isn't really a "variable" holding a struct. It's a **pointer to a memory location** that holds the struct.

### Storage classes

The word after `OpTypePointer` (`Private` above) is the **storage class**: where the memory lives. (LLVM calls this an *address space*.) Each kind of HLSL variable gets its own:

| HLSL | Storage class |
| --- | --- |
| `ConstantBuffer<MyStruct> uniformBuffer;` | Uniform |
| `RWStructuredBuffer<float> output;` | StorageBuffer |
| `groupshared float sharedMemory[64];` | Workgroup |
| `static MyStruct privateVar;` | Private |
| `MyStruct localVar;` (inside a function) | Function |

An important rule for `OpVariable`: its type must be an `OpTypePointer`, and both must name the same storage class.

<HlslSpirv html={opVariableRules} />

### `OpLoad` and `OpStore`

Since a variable is a pointer, reading and writing it always go through that pointer. `OpLoad` takes a pointer and gives you the value stored there. `OpStore` takes a pointer and a value, and writes the value there.

<HlslSpirv html={loadStore} />

## Calling SPIR-V directly from HLSL

These attributes do all the work: `vk::ext_instruction`, `vk::ext_literal`, `vk::ext_reference`, and the pair `vk::ext_capability` / `vk::ext_extension`. Each one changes how DXC turns a function declaration, or one of its parameters, into SPIR-V.

### 1. vk::ext_instruction

Put `[[vk::ext_instruction(opcode)]]` on a function declaration with no body. Every call to it becomes exactly that one instruction, right where the call is. The function's return type becomes the instruction's result type, and each argument becomes an operand. With a second argument naming an *extended instruction set*, such as `"GLSL.std.450"`, the call becomes `OpExtInst` instead.

<HlslSpirv html={extInstruction} />

Each argument is passed by value: DXC reads it first and uses the result as the operand. The next two attributes change that.

You might be wondering what happens if you change the argument and return types. DXC still compiles that for you, but in some cases the SPIR-V validator will stop you. For example, if you change `uint32_t` to `uint64_t` on `myBitReverse` above, you get:

<HlslSpirv html={extInstructionError} />

### 2. vk::ext_literal

Some operands aren't values at all. They're plain numbers written inside the instruction, such as an index or an option; the SPIR-V spec calls them *literals*. `[[vk::ext_literal]]` on a parameter makes DXC write the argument as a number. It has to be known at compile time.

<HlslSpirv html={extLiteral} />

Forget `[[vk::ext_literal]]` and DXC writes the *id* of the constant `1` into that slot instead. Every tool reading the instruction then sees whatever number that id happens to have:

<HlslSpirv html={extLiteralError} />

The 5 is an id number, so it changes between compilers and even between unrelated edits. If it happens to be in range, nothing complains and the wrong component is read.

### 3. vk::ext_reference

Some instructions need a pointer: `OpLoad`, `OpStore` and every atomic. From the recap, a variable already *is* a pointer. `[[vk::ext_reference]]` on a parameter passes the argument's pointer instead of reading its value. So the argument must be something that has a pointer: a variable, not a temporary.

<HlslSpirv html={extReference} />

A temporary has no pointer, so DXC refuses it:

<HlslSpirv html={extReferenceError} />

A normal HLSL function with an `inout` parameter passes that pointer through as well, so you can wrap these calls in your own helper functions.

### 4. vk::ext_capability and vk::ext_extension

An instruction from a SPIR-V extension only works if the module declares it: `OpExtension` for the extension and `OpCapability` for the feature. For HLSL's built-in functions DXC adds these lines itself. For your own declarations you add them with these two attributes. They're only emitted if the function is actually called.

<HlslSpirv html={extCapability} />

Without the two attributes, DXC still emits the instruction, but the validator rejects the module:

<HlslSpirv html={extCapabilityError} />

These lines only declare what the shader needs. The device still has to support the feature, here `VK_KHR_shader_clock`, when you create the pipeline.

## Where things stand

Written around **October 2026**, against **DXC's main branch**. Clang's HLSL support hasn't come out yet.

Inline SPIR-V started as DXC's version of GLSL's [GL_EXT_spirv_intrinsics](https://github.com/KhronosGroup/GLSL/blob/main/extensions/ext/GLSL_EXT_spirv_intrinsics.txt) and is documented on the [DXC wiki](https://github.com/microsoft/DirectXShaderCompiler/wiki/Inline-SPIR%E2%80%90V). It's being standardized in HLSL proposal [0011](https://github.com/microsoft/hlsl-specs/blob/main/proposals/0011-inline-spirv.md), still under review, but it's already available in DXC. It only applies when compiling to SPIR-V.
